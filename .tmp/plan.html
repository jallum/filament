RFC / 001
The rule
Tests use examples. Examples use the framework. We build four showcase apps — Todo, Cart, Inventory, Collaboration — and the test suite imports them directly. If the framework changes shape, the examples break, which means the tests break. No pretend units in isolation; the dogfood is the spec.
§ 01

The track map

Nine tracks. Three are on the critical path — B (core runtime), D (observables), and F (test harness). Tracks G and H are the dogfood layer: examples followed immediately by tests that exercise them. Nothing in H closes until the example it tests is in a state you'd show someone.

§ 02

The tracks

Track A · Infrastructure

Project scaffold

Everything needed before a line of framework code ships: Mix project layout, CI, Hex publishing config, ExDoc skeleton, and a .gitignore that excludes .tmp/.

  • A1 mix new filament --module Filament, supervision tree, dependencies pinned
  • A2 CI: GitHub Actions matrix (Elixir 1.17+, OTP 26/27), dialyzer, credo
  • A3 ExDoc config, logo, extras/ guides skeleton, hex.pm metadata
  • A4 CHANGELOG.md, CONTRIBUTING.md, mix.exs :package block
Track B · Core runtime ★ critical path

Fiber tree & reconciler

The fiber data structures, the tree-walk render loop, keyed reconciliation, and the ~F sigil that compiles templates to LiveView's static/dynamic IR. The hardest single piece of work in the project (see §05 risks).

  • B1 %Filament.Fiber{} struct — id, props, hook_slots, children, key
  • B2 VNode types: element, component, text, list (keyed)
  • B3 Render walk: (fiber, props) → vnode_tree, pure
  • B4 Reconciler: mount, update, unmount; keyed diffing for lists (missing key = compile error)
  • B5 ~F sigil macro — parse HEEx-compatible template, emit static/dynamic IR that feeds Phoenix.LiveView.Diff unchanged
  • B6 defcomponent macro — prop declarations, typespec generation, render/1 contract
  • B7 LiveView adapter: fiber tree → diff producer, plugs into existing socket
Track C · Hooks

UI state hooks

Hook slot infrastructure on the fiber, then the three hooks that cover local UI state. No framework dispatch; hooks are just indexed slot reads/writes on the current fiber during render.

  • C1 Hook slot infrastructure — slot index, read/write during render, stable across re-renders
  • C2 use_state(initial) → {value, setter}
  • C3 use_memo(fn, deps) — memoized derived value
  • C4 use_effect(fn, deps) — side-effect on mount/update/unmount
Track D · Observables ★ critical path

Domain state subscriptions

The Filament.Observable behavior, the Observable.GenServer default macro (subscriber tracking, monitors, projections, change notification), and the use_observable hook that wires a fiber to a live process.

  • D1 Filament.Observable behavior — handle_subscribe/3, handle_unsubscribe/2
  • D2 Filament.Observable.GenServer macro — subscriber list, monitor refs, notify_observers/1
  • D3 Projection support — per-subscriber project: fn, change-or-bust (skip notify if projected value unchanged)
  • D4 use_observable(server, topic, opts) hook — subscribe on mount, unsubscribe on unmount, re-subscribe on reconnect
  • D5 Backpressure: detect saturated mailbox → drop + re-subscribe on next render
Track E · Holds & Events

Resource holds & typed events

The use_hold hook, the defevent typed payload macro, and the closure-based event dispatch system that replaces LiveView's flat string handlers.

  • E1 use_hold(server, request) — acquire on mount, :DOWN-released on unmount, re-acquire after reconnect
  • E2 defevent macro — struct, encoder/decoder, typespec, compile-time field validation
  • E3 Event closures on fibers — on_click / on_submit capture lexical scope, compile to {node_id, event, payload} wire message
Track F · Test harness ★ critical path

The four-rung test API

A test support library mirroring Phoenix.LiveViewTest in feel but operating at the fiber level. Rungs 1–2 have no WebSocket; rung 3 connects a real observable; rung 4 is the familiar LiveView E2E. This is the layer that makes examples into tests.

  • F1 Rung 2: Filament.Test.mount/2 — mount a single fiber with props and stubbed observables. click/2, submit/2, render_text/1, has_class?/3
  • F2 Rung 3: subtree mount with a real (test-started) observable. eventually/1 assertion helper with timeout
  • F3 Rung 4: thin wrapper around Phoenix.LiveViewTest for host LiveView integration tests
  • F4 Observable stub builder — stub: [{Server, fn _ → ... end}] syntax, injected at mount time
Track G · Examples (dogfood)

Four showcase apps

Each example lives in examples/ as a standalone Phoenix app. They are not toys — they are meant to be the canonical illustration of each capability, and they are what the test suite imports. See §03 for details.

  • G1 TodoList — stateless components, use_state for filter/new-item input
  • G2 Cart & Checkout — use_observable with projections (badge vs full view), direct GenServer mutations
  • G3 Inventory holds — use_hold in CheckoutLineItem, process-death release, out-of-stock UX
  • G4 Collaboration locks — pessimistic document locking, typing indicators as monitored PID counts
Track H · Tests (using examples)

Test suite exercising examples

Tests live in test/ of the main lib but import modules from examples/. If an example compiles but the tests fail, the framework regressed. If an example won't compile, we have a design problem worth solving before shipping.

  • H1 TodoList: rung-1 domain tests + rung-2 component isolation (filter, add, toggle)
  • H2 Cart: all four rungs demonstrated end-to-end; projection tests (badge vs full view re-render budget)
  • H3 Inventory: rung-1 process-death → release; rung-2 CheckoutLineItem renders out-of-stock on {:error, :insufficient}
  • H4 Collaboration: rung-3 subtree; lock released on process death; presence count tracks live PIDs
Track I · Docs & Interop

Guides, HexDocs, and LiveView migration

Hexdocs generated from moduledocs. Narrative guides built around the four examples. Interop adapter (embed Filament in LiveView and vice versa). Migration guide covering the assigns-to-observables lift. This track opens after G and H are stable.

  • I1 HexDocs: all public modules documented, typespecs verified by dialyzer
  • I2 Guide: "Your first component" (TodoItem, rung-2 test)
  • I3 Guide: "Observing domain state" (Cart example walkthrough)
  • I4 Guide: "Resource holds" (Inventory example, the `:DOWN` pattern)
  • I5 LiveView interop adapter: <Filament.Component> inside a LiveView; a Filament fiber hosting a LiveComponent
  • I6 Migration guide: extract assigns into GenServer; phased codemods where automatable
§ 03

The examples

Each example is chosen to put exactly one capability under pressure. TodoList is the simplest possible real app — it validates the component model without any observables. Cart validates observables. Inventory validates holds. Collaboration validates the monitoring system under concurrent load. Together they cover the full API surface.

Example G1 · Simple

TodoList

Classic todo app. Stateless TodoItem components receiving an on_toggle closure. A TodoList parent managing filter state and new-item input with use_state. No GenServers, no observables — just the component tree and hooks.

Validates: defcomponent, props, use_state, event closures, keyed list rendering.

use_state defcomponent on_click :key
Example G2 · Observables

Cart & Checkout

A Cart.Server GenServer observable with two views: CartBadge subscribing to item count only (projection), and CartView subscribing to the full cart. Mutations (add_item, remove_item) are direct GenServer calls from event closures. Validates that projection prevents unnecessary re-renders.

Validates: use_observable, projections, Observable.GenServer, mixed UI + domain state.

use_observable use_state project: Observable.GenServer
Example G3 · Holds

Inventory holds

An Inventory.Server with explicit hold tracking. CheckoutLineItem calls use_hold and renders either a checkout button or an out-of-stock message. Closing the tab (simulated by killing the fiber process in tests) immediately restores available inventory — no TTL, no cleanup job.

Validates: use_hold, monitor lifecycle, :DOWN → release, out-of-stock UX path.

use_hold Process.monitor :DOWN use_observable
Example G4 · Concurrency

Collaboration locks

A shared document with pessimistic locking. A Document.Server tracks who holds the lock and how many users are present (typing indicators as a count of monitored PIDs). Disconnect releases the lock and decrements presence instantly. Multiple concurrent connections tested via Filament.Test mounting multiple fibers against a shared server.

Validates: Multi-client concurrency, presence as PID count, lock release on disconnect, rung-3 subtree tests with real server.

use_hold use_observable multi-client presence
§ 04

The test ladder

From the proposal. Each rung is independently meaningful; rungs 1–2 are the default, not the fallback. The test harness (Track F) exists to make rungs 1–3 cheap enough that rung 4 stays rare.

Domain logic

Rung 1 · Fast

Pure OTP. Start a GenServer with start_supervised!, drive it with calls, assert against returned state or via get_state. No UI, no fiber, no mount. The bulk of business-logic tests live here.

Used by: H1 (TodoList store), H2 (Cart.Server), H3 (Inventory — process death releases hold), H4 (Document lock).

→ examples/inventory, examples/cart

Component, isolated

Rung 2 · Fast

Mount one fiber with props and optionally a stubbed observable. Drive events with click/2 or submit/2. Assert with render_text/1 or has_class?/3. No real GenServer started. No WebSocket.

mount(CartView, cart_id: "c-1", stub: [{Cart.Server, fn _ → %Cart{items: []} end}])

→ examples/todo, examples/cart (CartBadge), examples/inventory (CheckoutLineItem)

Subtree

Rung 3 · Medium

Mount a parent with a real observable started for the test. Push changes through the GenServer; assert downstream components re-render. Catches observation-contract bugs and projection bugs. Uses eventually/1 since updates are async.

Key test: add an item to Cart.Server, assert CartBadge re-renders and CartSummary does not (projection working).

→ examples/cart (rung-3 canonical), examples/collaboration

End-to-end

Rung 4 · Slow

Familiar Phoenix.LiveViewTest-shaped test using a host LiveView. Reserved for routing, mount lifecycle, real wire-protocol behavior, and reconnect scenarios. Rare, not default.

→ one per example app for smoke coverage only
§ 05

Known risks

From the proposal's open questions, plus two we add for the build.

  • ~F sigil and static/dynamic preservation (B5)

    The most technically delicate task. LiveView's wire format is tiny because static template chunks are sent once per connection. A naïve fiber implementation that re-renders subtrees to strings on every update will blow up the wire format. The ~F sigil must preserve the static/dynamic split per component instance, not just per LiveView. This constrains what the macro can return and how it processes the template. Block B5 on a spike: manually produce the IR that Phoenix.LiveView.Diff expects, verify the wire output is identical, then write the macro to match.

  • Hook slot stability across reconciliation (C1)

    Hook slots must be stable across re-renders of the same fiber (same key). If reconciliation assigns a new fiber ID to what is conceptually the same component instance, hooks reset. The reconciler (B4) and hook slot infra (C1) need a shared definition of "same instance." Keyed lists solve it for explicit keys; keyless position-based matching is the edge case to nail down before writing hooks.

  • Cross-cluster scope of monitors (honest limit)

    Process monitors are reliable within a single BEAM cluster. They degrade across regions and behind certain network partitions. Holds and observable subscriptions are cluster-scoped primitives. The framework should surface this clearly in docs — not as a disclaimer buried in a footnote but as a first-class concept in the Observable module docs. Globally distributed apps will need heartbeat semantics layered on top; this should be opt-in, not the default cost everyone pays.

  • LiveView interop ordering (I5)

    Embedding a Filament fiber inside a regular LiveView requires the fiber tree's diff output to be acceptable to LiveView's existing reconciler. The reverse — a Filament fiber hosting a LiveComponent — is harder because LiveComponent has its own identity model. De-risk I5 by keeping the scope to one direction first (Filament inside LiveView) and treating the reverse as a Phase 2 concern.

§ 06

How to execute

Each track becomes an epic in beadwork. Each task becomes a child. Dependencies are wired explicitly so bw ready always gives you the honest next unblocked step.

  1. Materialize epics

    One bw create per track (A–I), type epic. Include the track description and its upstream dependencies. This is the planning artifact that survives compaction.

  2. Create child tasks

    One task per lettered item (A1, B3, D2…). Use --parent <epic-id>. Description should be concrete enough to start without re-reading this document.

  3. Wire blocking dependencies

    bw dep add <blocker> blocks <blocked> for the critical-path edges: A→B, B→C, B→D, C+D→F, F→G, G→H, H→I. Don't over-specify within a track — intra-track ordering is handled by working top-to-bottom.

  4. Spike B5 first

    Before touching any other Track B work, spike the ~F sigil against a real Phoenix app. Manually produce the static/dynamic IR and verify wire output. This de-risks the entire schedule — if B5 is harder than expected, we know before we've built everything that depends on it.

  5. Keep G and H in lockstep

    Don't let examples get more than one track-task ahead of the tests that exercise them. An example that runs but has no tests is a fixture, not a proof. Close H tasks immediately after G tasks.

  6. Gate I on H being green

    Don't write docs for an API that might still change. Track I opens only when all four H test suites are passing on CI. The examples become the narrative substrate for the guides — no separate tutorial apps needed.
